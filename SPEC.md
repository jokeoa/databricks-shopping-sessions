## Overview

Задача трека — одна пакетная программа в Docker-образе. Она читает грязные CSV
из `/data` и пишет в `/output` две Parquet-таблицы, `user_daily` и
`campaign_daily`. Ответ должен совпасть с эталоном строка в строку. Среди
верных ответов побеждает самый быстрый.

Предлагается:

*   **Рабочий путь** — один Rust-бинарник без внешнего движка. Он:
    1.  разбирает CSV из байтов по диалекту `rules.md`;
    2.  дедуплицирует события по `event_id` до того, как раскладывать их по
        людям;
    3.  находит человека через отображение ссылок, которое строится один раз и
        дальше только читается;
    4.  раскладывает события и клики по человеку;
    5.  для каждого человека вычисляет сессии и кредит, а для каждой активной кампании сессии — один ассист;
    6.  пишет две таблицы.
*   **Оракул** — отдельная медленная программа на Python. Она пишется буквально
    по `rules.md` и в образ не входит. Её задача — сверка на малых и средних
    наборах.
*   На 20M и 60M проверяются неизменность результатов при преобразованиях, судьбы физических строк,
    имена из полного графа, выбранные сессии и обе выходные таблицы. Независимая свёртка вкладов всех
    людей проверяет распределение метрик по кампаниям. Для полного Python-оракула на 20M предусмотрен
    отдельный ограниченный эксперимент.
*   **Первая отправка** — простая версия на том же Rust. Она служит запасной
    отправкой и эталоном этапов для быстрого пути.

Сейчас в репозитории лежит заготовка на Python и DuckDB, которая пишет пустые
таблицы [Факт: `Dockerfile:4-14`, `run.sh:8`]. Тестовый стенд (фикстуры,
скрипты сверки, dev-ответ, генератор) лежит в `.local/`. Этот каталог исключён
и из git, и из контекста Docker-сборки [Факт: `.gitignore:1`,
`.dockerignore:2`].

### Термины

| Термин | Значение |
| --- | --- |
| ID, `user_id` | Одна строка из колонки `user_id`, `user_id_a` или `user_id_b`. Сравнивается побайтово, без нормализации |
| человек (person) | Группа ID, склеенная ссылками. Все правила о сессиях и кликах говорят о человеке [Факт: `rules.md:40`] |
| имя человека | Побайтово наименьший ID группы. Это значение колонки `user_id` в выходе [Факт: `rules.md:44`, `rules.md:78`] |
| копия события | Строка с тем же `event_id`, что у другой строки. Копии могут называть разных пользователей [Факт: `rules.md:121`] |
| оракул (oracle) | Медленная буквальная реализация `rules.md` для сверки. В образ не входит |
| ассист (assist) | Кампания с подходящим кликом в 7 днях до начала сессии [Факт: `rules.md:66`] |
| whale | Человек с 1–2% всех событий или кампания с большой долей кликов [Факт: `rules.md:105`, `rules.md:111`] |
| общее устройство (shared device) | ID, который ссылками склеивает тысячи людей в одного [Факт: `rules.md:108`]. В исходниках генератора это `kiosk`. В коде, логах и тестах используется термин из `rules.md` |
| ключ ID | 16-байтовое представление ID, которое сохраняет побайтовый порядок (см. Technical Plan) |
| корзина (bucket) | Часть записей, отобранная по хешу ключа. Обрабатывается одним потоком |

## The Problem

### Условия

*   **Контейнер:**
    *   8 vCPU — гиперпотоки Intel Xeon, есть AVX-512;
    *   24 GB памяти без свопа;
    *   нет сети;
    *   корень файловой системы только для чтения, `/tmp` — 64 MB в памяти;
    *   процесс запускается от uid 1000;
    *   писать можно только в `/output` и `/scratch`.

    [Факт: `starter README:52-62`]
*   **Сборка.** Скорер сам собирает `Dockerfile` из публичного репозитория на
    amd64, по указанному SHA или по последнему коммиту ветки по умолчанию.
    Время сборки не считается. Считается время от старта контейнера до выхода
    [Факт: `starter README:46-48`].
*   Условия скоринга по [описанию трека](./.local/track_outline.md).

    | Стадия | Объём | Лимит | Что видно при ошибке |
    | --- | --- | --- | --- |
    | Dev | 1M событий, публичный seed 1 | 3 мин | Различающиеся строки и логи |
    | Практика | ~20M событий | Меньшее из 2× baseline и 5 мин. Один замер, три при первом результате строго меньше 20 с | Код выхода, флаг OOM, число missing, extra и differing |
    | Финал | ~60M событий, новые данные | 3 мин на каждый из 3 прогонов, балл — медиана | То же. Один прогон дольше 3 мин — нет балла |

    Первые 10+ мест перезамеряются 9 раз на простаивающей машине. Разброс
    времени между машинами до ~20%. Две отправки в час.

### Почему задача трудная

1.  **Правильность проверяется вслепую.**
    *   На практике и в финале не видно ни логов, ни значений.
    *   Регистр ID, общие устройства и исправление пользователя в копии встречаются с разной частотой.
        Корректность проверяется ручными случаями и воспроизводимыми усиленными наборами. Частоту на
        скрытом seed заранее установить нельзя.
    *   Эталонный ответ есть только к dev и к 36 фикстурам.
2.  **Данные приходится перегруппировать дважды.**
    *   Копии одного события могут называть разных пользователей, а побеждает
        копия с наименьшим `ingest_ts`. Поэтому сначала нужна группировка по
        `event_id`, без оглядки на пользователя [Факт: `rules.md:51`,
        `rules.md:121`].
    *   Строки перемешаны по файлам, поэтому затем нужна вторая группировка, по
        человеку [Факт: `rules.md:115`].
    *   Публичная E4 уже обнаруживает дедупликацию по пользователю — две копии одного события относятся
        к разным людям. Сочетание этой ошибки с невалидным ранним победителем проверяет отдельная
        фикстура. [Входы и ожидаемые строки E4](./.local/starter-duckdb/fixtures/E4/).
3.  **Физическая строка CSV имеет свой контракт.** LF завершает строку, CR сохраняется как байт поля.
    Кавычки допустимы вокруг всего поля, декодированная пустая строка означает null. Пробелы значимы, в
    числах допустимы ASCII-цифры. Стартер показывает расхождения CSV-ридера DuckDB и отдельно
    предупреждает о Unicode-цифрах в регулярных выражениях Polars. Общий разборщик проверяется на
    конкретных примерах из правил и фикстур. Время разбора измеряется отдельным таймером.
    [Правила CSV](./.local/rules.md) и [замечания стартера](./.local/starter-duckdb/README.md).
4.  **Нет свопа.**
    *   Перерасход памяти означает OOM и потерю отправки, а не замедление.
    *   На Mac есть своп и сжатие памяти, поэтому локальный прогон превышение не
        покажет.
5.  **Финал идёт на новых данных.**
    *   Свойства конкретного генератора — это не правила. Например, ID не
        длиннее 9 байт, нет `\r`, окно начинается в полночь.
    *   Генератор уже менялся [Факт: `user.rs:401-405`].

### Что предлагается

Скорость решает Rust-бинарник. Он делает два перемещения данных: сначала по
ключу события, затем по человеку. Вся остальная работа идёт в корзинах,
независимо на каждом ядре. Уверенность в правильности дают:

*   на малых и средних наборах Python независимо вычисляет обе таблицы;
*   на 20M и 60M сверяются построчный разбор и полный граф ссылок, для выбранных людей — `user_daily` и
    сессионные вклады из большого прогона. Из всех вкладов Python заново агрегирует `campaign_daily`.
    Метаморфные тесты и встроенные самопроверки дополняют эти сверки.

5–10 с на полном входе 60M с тёплым кэшем и 8 vCPU — непроверенная гипотеза. Фаза 1 измеряет чтение и
разделение полей. Первое свидетельство о сквозном времени появляется на полном драйвере с двумя
проверенными выходами и сопоставимыми холодными и тёплыми запусками.

## Goals

Каждая цель проверяется числом или однозначным результатом.

1.  **Точное совпадение.**
    *   `MATCH` на dev.
    *   0 missing, 0 extra и 0 differing на практике.
    *   Каждый из 3 финальных прогонов совпадает.
2.  **Внутренний запас по времени.** На Linux-VM класса n2 с 8 vCPU проект требует не более 120 с в
    каждом из трёх холодных и трёх тёплых сквозных прогонов 60M. Официальный предел финала — 180 с на
    **каждый** из трёх запусков, балл определяется медианой. При сопоставлении с практикой сохраняются
    объём, машина и состояние кэша. [Условия трека и оценка запаса](./.local/track_outline.md).
3.  **Целевое время задаётся после первой засчитанной отправки.**
    *   Сейчас цель по скорости измерить нельзя: времена лидеров и baseline
        неизвестны [Факт: `outline:202`].
    *   После фазы 3 числовая цель для медианы на 60M записывается в Decision
        Log по доске практики. До этого момента цель — только порог из
        пункта 2.
4.  **Пиковая память.** `memory.peak` свежей cgroup v2 каждого квалифицируемого режима укладывается в
    проектный бюджет на 60M и 120M без свопа и OOM. Начальное значение — 12 000 000 000 байт. Полная
    процедура в разделе 9.
5.  **Допуск к отправке.** `make presubmit` проверяет точный SHA и выполняет строку
    для режима кандидата из [таблицы допуска](#qualification). Первый `simple`
    проходит её в фазе 3. Кандидат `fast` проходит расширенную проверку в фазе 4.
    Результат проверки относится к указанным SHA, образу и режиму.
6.  **Обработка ошибок.** Парсер возвращает результат или причину отбрасывания для произвольных байтов.
    `main` переводит возвращённые ошибки конфигурации и ввода-вывода в коды 2–4. Исчерпание памяти и
    внешнее завершение процесса фиксирует стенд.
7.  **Диагностика.** Между сопоставимыми прогонами первая разошедшаяся граница локализует поиск. Для
    каждой мутации требуется зафиксированный провал конкретного теста на фикстуре или T2. Совпавшая
    строка в реестре сама по себе не подтверждает обнаружение.

## Non-Goals

1.  Поддержка CSV за пределами диалекта `rules.md:22`.
2.  Рабочая сборка под arm64. Она нужна только для локального цикла
    разработки.
3.  Потоковый или инкрементальный режим.
4.  DuckDB, Polars или другой внешний движок в рабочем пути. Запасная отправка
    тоже на Rust (D4), поэтому исключения нет.
5.  Go в каком-либо пути.
6.  Ускорения, которые опираются на свойства генератора без проверки во время
    работы и без общего запасного пути. Свойства генератора — не правила.
7.  Сопоставление ID по сходству или нечёткое.
8.  Штатный сброс записей на диск. При превышении измеренной границы нужна отдельная проверенная
    переработка до допуска.
9.  Вторая независимая быстрая реализация. На T4 её стоимость сопоставляется с независимыми проверками
    B1/B2, выбранных сессий и полной агрегации кампаний.
10. Обязательный полный Python-прогон на 60M. Оценка около 30 GB относится к 60M. Полный оракул на 20M
    испытывается отдельно на одном указанном наборе с заранее записанными лимитами памяти и времени и
    измерением пика. При успехе сравниваются обе таблицы, при остановке сохраняются достигнутый объём,
    время, пик и причина. Обязательные проверки T4 выполняются в обоих случаях.
11. Оракул и отладочные инструменты в образе отправки.
12. Подгонка под конкретный seed.

## Open Questions

Решения, которые зависят от замеров:

*   **D6. Память и чтение.** Начальный бюджет 12 000 000 000 B. Фаза 1 сравнивает `mmap` и `pread` на
    одинаковых байтах. Бюджет и аллокатор оцениваются только на полных драйверах, с 60M и 120M по
    разделу 9. Пересмотр до 16 000 000 000 B требует отдельного решения и повторного допуска.
*   **D8. Целевой CPU и libc.**
    *   Базовая сборка x86-64-v2 или v3.
    *   Цель `x86_64-unknown-linux-gnu` с образом `debian-slim` или musl с
        mimalloc.

    Решает замер.
*   **D9. Ручной SIMD.** Числовое условие, при котором делать ручной SIMD,
    задаётся после фазы 1. Пример формы: «нижняя граница разбора выше X с на
    60M, а нижняя граница чтения ниже Y с».

Вопросы организаторам:

1.  Показывает ли скорер счётчики missing, extra и differing после ненулевого
    кода выхода?
2.  Можно ли делать диагностические отправки с намеренным несовпадением на dev?
3.  Счётчики на скрытых прогонах даются по каждой таблице или общим итогом?
4.  Финальные данные делает та же версия генератора?
5.  Как трактовать последнюю строку файла без `\n`?
6.  Поддерживает ли среда сборки нужные инструкции Dockerfile?
7.  Как выбирается финальная попытка, до какого срока можно изменить выбор и возможна ли повторная
    отправка прежнего SHA? Источник, дату и подтверждение сохранить в `spec/scoring.md`.

Вопросы дизайна:

*   **Насколько независим оракул.**
    *   Оракул и быстрый путь пишет один автор с одним AI-ассистентом, в одной
        сессии, по одному прочтению `rules.md`.
    *   Сверка ловит расхождение двух реализаций, но не общую ошибку
        прочтения.
    *   Независимую истину дают только 36 фикстур и dev-ответ.
    *   Мера пока одна — реестр правил с проверкой автором правило за правилом.
        Нужна ли вторая мера, не решено.

## Critical User Journeys (CUJs)

### CUJ 1: Прогон скорера на финальных данных

*   **Given:** скорер собрал образ из выбранного коммита на amd64. В `/data`
    смонтирован новый набор на ~60M событий. Заданы лимиты контейнера и
    переменные `DATA_DIR`, `OUTPUT_DIR`, `SCRATCH_DIR`, `NCPU=8`, `MEM_GB=24`.
*   **When:** контейнер запускает `CMD` без аргументов, 3 раза подряд.
*   **Then:**
    *   каждый прогон пишет в `/output/user_daily/` и
        `/output/campaign_daily/` хотя бы по одному `.parquet` и выходит с
        кодом 0;
    *   таблицы совпадают с эталоном;
    *   каждый локальный квалификационный прогон укладывается в 120 с, для финального скоринга действует
        предел 180 с;
    *   на Linux-стенде `memory.peak` укладывается в байтовый бюджет D6;
    *   после успешного выхода в `/output` остаются только закрытые таблицы, рабочие данные хранятся в `/scratch`.

### CUJ 2: Проверка перед отправкой

*   **Given.** У автора чистое рабочее дерево и тег на SHA кандидата.
*   **When.** Автор запускает `make presubmit`.
*   **Then.** Стенд собирает этот SHA, запускает образ без аргументов через
    официальный `docker_run.sh` и считывает фактический режим из стартового JSON.
    Выполняются все проверки соответствующей строки [таблицы допуска](#qualification).
    Ошибка останавливает отправку. Для упавшей фикстуры стенд указывает набор,
    ID и её запись «Catches». Для dev он показывает расхождение двух таблиц.
    Квитанция с SHA, образом и результатами остаётся в `work/qualification/`.

### CUJ 3: Поиск расхождения на объёме

*   **Условие.** На 20M сработала метаморфная проверка либо сверка выбранных людей.
*   Для одинаковых байтов запускают `diff_stages.py A B --profile identical`, для преобразованного входа
    — `--profile transform`. При сравнении выборки берут выбранные B5 из полного прогона и независимо
    свёрнутую полную таблицу кампаний. Порядок и ключи границ определены в разделах 12–13.
*   По имени из первой разошедшейся сессии запускают `DATA_DIR=... shopping-sessions explain <user_id>`
    и аналогичную позиционную команду Python. Вывод показывает экранированные байты имени и ключей, файл
    и числовое смещение, членов компоненты, копии события, выбранный клик и ассисты.

### CUJ 4: Слепой провал на практике

*   Практика может вернуть код выхода, OOM и счётчики missing/extra/differing без строк. Автор сохраняет
    поля в том виде, который показал скорер, включая разбивку по таблицам, если она есть.
*   Словарь локальных мутаций может дать ноль, одну или несколько гипотез. Другой seed, набор ошибок или
    объединение счётчиков меняют картину. До исправления требуется воспроизвести расхождение на
    конкретной локальной фикстуре или наборе. При нескольких гипотезах выбирают вход, на котором их
    результаты различаются. При отсутствии совпадений исходят из нарушенного правила, граничных случаев
    и дампов.

### 2. Поток данных быстрого драйвера

```text
/data ─┬─ manifest.json, products.csv, campaigns.csv ──► Шаг 0: справочники (после старта только чтение)
       ├─ links/*.csv ──► разбор ссылок → union-find → замороженное отображение «ключ ID → ключ имени»
       │                  (идёт одним потоком параллельно шагу 1, нужно к шагу 2)
       └─ events/*.csv, clicks/*.csv
              │
              ▼
   Шаг 1 (T потоков; единица работы — кусок файла)
     строка события → EventRaw (с кодом судьбы) ──► корзина событий hash(ключ event_id)   [T × E векторов]
     строка клика   → проверка → ClickRec(ключ user_id) ──► вектор потока
              │ барьер 1
              ▼
   Шаг 2 (T потоков; единица работы — корзина событий)
     копия с наименьшим ingest_ts → её код судьбы → ключ user_id → ключ имени
       ──► EventRec ──► корзина людей hash(ключ имени)                                  [T × P векторов]
     ClickRec: ключ user_id → ключ имени ──► корзина людей
              │ барьер 2
              ▼
   Шаг 3 (T потоков; единица работы — корзина людей, крупные первыми)
     локальные номера → сортировка → sessionize → credit и assists
       ──► строки user_daily (свой Parquet-файл потока)
       ──► массив [кампания × день] потока
              │ барьер 3
              ▼
   Шаг 4 (один поток)
     слияние массивов → campaign_daily → самопроверки → счётчики в stderr → код выхода
```

Почему шагов именно столько:

*   **Первое перемещение — по ключу события.** Копии одного события могут
    называть разных пользователей, а побеждает копия с наименьшим `ingest_ts`
    независимо от пользователя. Это проверяется публичной E4 (`rules.md:51,121`).
*   **Второе перемещение — по человеку.** Строки человека разбросаны по файлам
    [Факт: `rules.md:115`].
*   **Клики первого перемещения не требуют.** Копии клика одинаковы
    [Факт: `rules.md:61`], поэтому проверку можно делать сразу при разборе,
    а дедупликацию не делать вовсе. Обоснование в разделе 7.
*   **Ссылки вне критического пути.** Они занимают ~50 MB [Оценка] и нужны
    только с шага 2.

Каждый логический этап — отдельная чистая функция над корзиной или над одним
человеком. Счётчики включены всегда. Дампы границ этапов включает только
cargo-фича `diag`, которая не попадает в сборку образа.

### 3. Представление данных

#### 3.1 Ключ ID

Все ID — `event_id`, `user_id`, `click_id`, стороны ссылок — хранятся как
16-байтовый ключ `IdKey` (D2).

*   **ID не длиннее 15 байт.** Байты 0–14 содержат ID, дополненный нулями,
    байт 15 — длину. Сравнение двух таких ключей как `u128` в big-endian даёт
    тот же результат, что побайтовое сравнение исходных строк. Пример: `u1` и
    `u1\0` различаются по байту длины.
*   **ID длиннее 15 байт (переполнение).** Байты 0–10 содержат первые 11 байт
    ID, байты 11–14 — порядковый номер в глобальной таблице переполнения
    (`u32`, big-endian), байт 15 — `0xFF`.
    *   Таблица под мьютексом сопоставляет полные байты с индексом. Текущий генератор формирует
        распространённые ID из префикса и от одного до восьми знаков base36 для 40-битного значения
        (`text.rs:192–216`). Длинные входные ID проходят через ту же декодируемую таблицу.
    *   Равенство ключей по-прежнему означает равенство ID: номер уникален.
    *   Если хотя бы один из двух ключей переполненный, сравнение уходит в
        медленную ветку. Она восстанавливает полные байты (из ключа или из
        таблицы) и сравнивает их.
*   **Где нужен порядок.** Побайтовый порядок нужен в трёх правилах: имя
    человека, ничья по `click_id`, ничья по `top_category`
    [Факт: `rules.md:44`, `rules.md:63`, `rules.md:83`]. Сравнение делает одна
    функция `key::cmp_bytes`. В её комментарии стоят ID правил
    `LNK.NAME_MIN` и `CL.TIE_CLICK_ID`.
*   **Тест свойства.** `key::cmp_bytes(encode(a), encode(b)) == a.cmp(b)` на
    случайных строках с NUL, `\r`, пробелами, табами, длиной 0–40 байт и
    общими префиксами длиннее 11 байт.

Отдельные типы-обёртки не дают перепутать понятия:

| Тип | Что хранит | Порядок |
| --- | --- | --- |
| `IdKey` | Ключ любого ID | Побайтовый, через `cmp_bytes` |
| `NameKey` | `IdKey` имени человека | Побайтовый, через `cmp_bytes` |
| `LocalPerson(u32)` | Плотный номер человека внутри корзины | Без смысла, только равенство |
| `CategoryRank(usize)` | Индекс в массиве имён категорий, включая `unknown` | Соответствует исходным байтам имени |
| `CampaignIdx(u32)` | Индекс кампании в `campaigns.csv`; `organic` получает индекс C, где C — число кампаний | Без смысла |

Голый `user` в идентификаторах не используется, кроме имени выходной колонки.

#### 3.2 Записи на границах этапов

| Запись | Поля | Размер | Где живёт |
| --- | --- | --- | --- |
| `EventRaw` | `event_id` и `user_id` (по 16), `ingest_ts` и `ts` (по 8), `CategoryRank` (8), цена u32, тип и код судьбы (по 1) | 64 B | Корзины событий, шаги 1–2 |
| `EventRec` | `NameKey` (16), `ts` (8), `CategoryRank` (8), цена u32, тип u8 | 40 B | Корзины людей, шаги 2–3 |
| `ClickRec` | ключ пользователя или имени (16), ключ клика (16), `ts` (8), `CampaignIdx` (4) | 48 B | Локальный вектор и корзины людей |

Размеры включают выравнивание на 64-битных целевых платформах. У записей `#[repr(C)]`, у типа события и
кода судьбы `#[repr(u8)]`. Проверки `size_of` входят в обе сборки.

*   **Код судьбы** вычисляется при разборе и зависит только от полей строки и
    окна. 0 значит «валидно и не опоздало». Иначе это код первой не
    выполненной проверки, в порядке из реестра правил (раздел 10).
*   Невалидная копия с ключом и разбираемым временем поступления сохраняет `EventRaw` до глобального
    выбора победителя. Один формат позволяет объяснить, почему более поздняя валидная копия не попала в
    результат.
*   **Записи не ссылаются на входные байты.** Поэтому прочитанные страницы
    входа можно сразу освобождать.

#### 3.3 Справочники (шаг 0)

*   **`manifest.json`.** Читается через `serde_json`. `window_start` и
    `window_end` разбираются тем же разборщиком F1, что и события.
*   **Дни.** Номер дня — `ts.div_euclid(86 400 000)`. Диапазон массивов дней —
    от `floor(window_start / день)` до `floor((window_end − 1) / день)`.
*   `products.csv` даёт отображение байтов ID в `CategoryRank(usize)`. Имена категорий объединяются с
    `unknown`, сортируются по байтам и нумеруются через `enumerate()` по реальному массиву, без
    сужающего преобразования. Тест с 65 536 разными категориями плюс `unknown` требует 65 537 различных
    рангов и проверяет побайтовую ничью по выручке с `unknown`.
*   **`campaigns.csv`.** Даёт таблицу «байты `campaign_id` → `CampaignIdx`» и
    массив каналов.
*   **Разбор справочников.** Оба файла разбираются тем же диалектом. Обе
    таблицы — `HashMap<Box<[u8]>, _>` с быстрым хешем (`foldhash`). Запись в
    них закончена до старта шага 1, дальше они только читаются.
*   **Ссылки.**
    1.  Разобрать строку из двух полей. Если строка повреждена или хотя бы
        один конец пуст (в том числе `""`), отбросить её до присвоения номеров.
        Так строки `u1,` и `,u3` из L3 оставляют `u1` и `u3` разными людьми.
    2.  Присвоить плотные номера двум непустым ID.
    3.  Объединить компоненты в union-find со сжатием путей. При объединении
        корнем становится компонента с побайтово меньшим именем.
    4.  Замороженная `HashMap<IdKey, NameKey>` только для ID из ссылок.

    ID, которого нет в отображении, — сам себе человек и имя
    [Факт: `rules.md:44`].

### 4. Шаги быстрого драйвера

**Шаг 1. Разбор кусков.**

*   **Нарезка.** Входные файлы режутся на куски по `SS_CHUNK_BYTES`.
    Значение по умолчанию подбирает фаза 1, кандидат — 16 MiB
    [Гипотеза: фаза 1].
*   **Очередь.** Куски всех папок стоят в одной общей очереди (атомарный
    счётчик). Потоки берут их по одному.
*   **Строки куска.** Куску `[s,e)` принадлежат только строки с первым
    байтом в этом интервале. `Source` возвращает признак `starts_on_line`:
    при `s=0` он истинен, в остальных случаях равен `file[s−1] == LF`. При
    ложном признаке пропускается фрагмент до следующего LF. Если в `[s,e)` нет начала своей строки,
    кусок пуст. Продлевать чтение за `e` может только
    владелец уже начавшейся строки, до LF или EOF. После последнего LF
    новая пустая строка в EOF не создаётся. Заголовок — запись со смещением 0.
*   **События.** Строка разбирается в `EventRaw`. Строка с пустым `event_id`
    и повреждённая строка отбрасываются со счётчиком причины. Запись
    дописывается в вектор `(поток, hash(ключ event_id) mod E)`.
*   **Клики.** После проверки числа полей и кавычек отбросить пустой
    декодированный `click_id`, затем проверить непустой `user_id`, время,
    окно кликов и наличие кампании. Только прошедшая эти проверки строка
    становится `ClickRec`. Пустой ID не участвует ни в кредите, ни в ассистах
    [Факт: `rules.md:60-66`, `user.rs:642-646`].
*   Оба читателя реализуют один контракт `Source`. Необязательная подсказка
    `posix_fadvise(..., POSIX_FADV_WILLNEED)` компилируется только в Linux. На Darwin `mmap` и `pread`
    выполняются напрямую. Стенд фиксирует фактически выбранный читатель и состояние кэша.

**Шаг 2. Корзины событий.** Для каждой корзины `b` (векторы `(t, b)` всех
потоков):

1.  Сортировка по `(ключ event_id, ingest_ts)`.
2.  Линейный проход оставляет первую копию каждого ключа.
3.  Если у оставленной копии код судьбы не 0, событие отбрасывается со
    счётчиком причины.
4.  Иначе ключ `user_id` переводится в `NameKey` через замороженное
    отображение. Получается `EventRec`, который дописывается в вектор
    `(поток, hash(NameKey) mod P)`.
5.  Векторы корзины `b` освобождаются сразу после обработки.

Потом так же обрабатываются векторы кликов: ключ `user_id` переводится в
`NameKey`, клик дописывается в корзину людей.

Копии с равным `ingest_ts` по правилам одинаковы [Факт: `rules.md:51`].
Счётчик `assume.equal_ingest_projection_diff` отмечает отличие только
сохранённых полей `EventRaw` у таких копий. Исходное написание цены, кавычек
или двух разных неизвестных товаров из этой записи восстановить нельзя.

**Шаг 3. Корзины людей.**

*   Очередь берёт корзины по убыванию размера, чтобы самый крупный человек начал обрабатываться раньше.
    Начальная настройка — 512 корзин. Время самой тяжёлой корзины, число событий, кликов и пар
    «сессия–кампания» измеряются на фактическом наборе.
*   **Локальные номера.** Каждый `NameKey` корзины получает `LocalPerson`.
*   **Ключ сортировки событий** — один `u64`: в старших 33 битах
    `LocalPerson`, в младших 31 битах `ts − (window_start − 7 дней)`.
    *   Это работает, пока `window_end − window_start + 7 дней < 2^31 мс`
        (~24.8 дня).
    *   Условие проверяется при старте (допущение `ASM.SORT_KEY_31`).
    *   Если оно не выполнено, сортировка идёт по паре `(LocalPerson, ts)`,
        растёт счётчик `assume.wide_window`.
*   **Сортировка событий.** Неустойчивая: порядок событий с равным `ts` на
    выход не влияет [Факт: `rules.md:54`].
*   **Сортировка кликов.** По `(LocalPerson, ts по возрастанию, click_id по
    убыванию через cmp_bytes)`. Тогда в окне подходящих кликов победитель
    атрибуции стоит последним (раздел 6).
*   **Обработка.** Для каждого человека по порядку:
    1.  `sessionize`;
    2.  `credit_and_assists`;
    3.  `aggregate_user_day`.
*   **Выход шага.** Строки `user_daily` поток копит в своём писателе Parquet.
    Счётчики «кампания × день» поток копит в своём плотном массиве
    `(C + 1) × D × 4` значений `i64`. На 2 001 × 14 дней это ~0.9 MB на поток
    [Оценка].
    *   Если `(C + 1) × D` больше 8M ячеек или вычисленная без переполнения общая ёмкость плотных
        массивов всех потоков превышает оставшийся бюджет, выбирается
        `HashMap<(CampaignIdx, день), счётчики>` (допущение
        `ASM.CAMPAIGN_DAY_DENSE`).

**Шаг 4. Завершение.**

1. Координатор завершает работу потоков и собирает их типизированные результаты. Каждая группа закрывает
   свои временные части `user_daily`, включая пустую часть для пустой таблицы.
2. По сумме локальных массивов формируются строки `campaign_daily` для ячеек с `sessions > 0` или
   `assisted_sessions > 0`. Писатель закрывает таблицу в той же выходной файловой системе.
3. После успешных записей и закрытий обе таблицы публикуются. Самопроверки выполняются по суммам и
   глобальным ключам. `main` печатает счётчики и возвращает соответствующий код. Протокол ошибок чтения,
   закрытия и публикации задан в разделе 11.

### 5. Простой драйвер

Простой драйвер пользуется тем же общим слоем:

*   разбор строки, время, цена;
*   `IdKey`;
*   справочники и ссылки;
*   `sessionize`, `credit_and_assists`, `aggregate_user_day`;
*   запись Parquet, счётчики, дампы.

Отличается он только потоком данных:

*   Целые файлы читает стандартный парсер. `HashMap<IdKey, EventRaw>` оставляет победителя по
    `ingest_ts` до проверки остальных полей.
*   Драйвер строит `HashMap<NameKey, (Vec<EventRec>, Vec<ClickRec>)>`. Перед вызовом общих функций
    каждый работник сортирует события человека по возрастанию `ts` и клики по возрастанию `ts`, затем по
    убыванию исходных байтов `click_id` (`cmp_bytes`). Этот порядок обязателен и для `fast`.
*   Очередь распределяет целых людей. Тест переставляет физические строки E2 и A5 и проверяет сессии и
    выбранный клик в каждом доступном драйвере.

`SS_MODE=simple|fast` выбирает реализованный драйвер. По умолчанию работает квалифицированный `simple`.
Правило смены режима по измерениям приведено в [матрице квалификации](#qualification).

**Что ловит сверка simple против fast** (следствие D10): только ошибки потока
данных. Это разбиение на куски, порядок дедупликации, разброс по корзинам,
слияние массивов. Ошибку в общей функции такая сверка не увидит. Общие
функции проверяют:

*   Python-оракул на seed;
*   ручные ответы к фикстурам и официальный dev;
*   на T4 — B1/B2, результаты и сессии выбранных людей, а также независимая свёртка всех сессионных
    вкладов в `campaign_daily`.

### 6. Разбор, время, сессии, атрибуция

**Строка CSV** (`csv::split_line`):

*   **Причины повреждения** проверяются в таком порядке:
    1.  пустая строка;
    2.  неверное число полей — 7 у событий, 4 у кликов, 2 у ссылок и
        справочников; поля делит каждая запятая, кавычки на это не влияют;
    3.  поле с кавычкой не на месте.

    Поле валидно, если в нём нет кавычек вообще, либо его длина не меньше 2, оно
    начинается и кончается кавычкой и внутри кавычек нет. Табличные тесты
    покрывают `"`, `""`, `"""`, `""x"`, `"x""`, `x"` и `"a,b"`.
*   **`\r`** — обычный байт значения. Пробелы входят в значение.
*   **Пустое поле** после снятия кавычек означает null.

**Время** (`ts::parse`):

*   **F1** занимает ровно 20 байт, **F2** — ровно 25 байт.
*   **Календарь** проверяется по записанным полям до вычитания смещения.
    Високосный год — по полному григорианскому правилу. Смещение: часы 00–23,
    минуты 00–59, двоеточие обязательно.
*   **F3** — только ASCII-цифры. Значение накапливается через `checked_mul` и
    `checked_add` в `i64`. Переполнение означает «вне окна», а не «плохой
    формат». Так E18 с 21 цифрой не заворачивается в отрицательное число.
*   **Результат** — тип-сумма: «миллисекунды», «плохой формат» или «вне
    окна». Окно проверяет вызывающая сторона, своё для событий и для кликов.

**Цена** (`price::parse`) проверяется только при `event_type == purchase`.
Покупке нужны ASCII-цифры и значение 1–10 000 000. Ведущие нули допустимы,
после них остаётся до восьми значащих цифр. Для `view` и `cart` поле
игнорируется и вклад в выручку равен нулю. В E10 остаётся просмотр с `-5`,
покупка с `19.99` отбрасывается [Факт: `rules.md:52`].

**`ingest_ts`** разбирается тем же строгим разборщиком F1. По правилам он
всегда валиден [Факт: `rules.md:34`]. Если разбор не прошёл, строка считается
повреждённой, а счётчик `assume.ingest_ts_invalid` растёт (толкование
`EV.INGEST_TS_INVALID`, раздел 10).

**Тотальность.** Все функции разбора принимают `&[u8]` и возвращают тип-сумму.
Индексация идёт только после проверки длины. Паника на входных байтах —
ошибка программы, которую проверяют fuzz-тесты.

**`sessionize`.**

*   События человека отсортированы по `ts`. Новая сессия начинается, когда
    `ts − ts_предыдущего > 1 800 000`. Равные `ts` дают разрыв 0, поэтому
    попадают в одну сессию [Факт: `rules.md:54`].
*   Сессия несёт:
    *   начало;
    *   день начала;
    *   число событий;
    *   выручку;
    *   признак покупки;
    *   суммы цен покупок по `CategoryRank`.

**`credit_and_assists`** — один проход двумя указателями `lo` и `hi` по
кликам человека, в порядке начала сессий.

*   **Вход в окно.** Клик входит в окно, когда `click.ts <= start`.
*   **Выход из окна.** Клик выходит, когда `click.ts < start − 604 800 000`.
*   **Один предикат.** Обе границы задаёт одна функция
    `qualifies(click_ts, start)`. На ней держатся и атрибуция, и ассисты
    [Факт: `rules.md:63`, `rules.md:66` описывают одно множество].
*   **Победитель атрибуции** — `clicks[hi − 1]`: наибольший `ts`, а среди
    равных — наименьший `click_id`, потому что внутри равного `ts` порядок
    убывающий. Если окно пусто, сессия уходит в `organic`.
*   Счётчики кликов и список активных кампаний обновляются при сдвиге окна. Для каждой сессии
    перебираются все разные кампании в окне, включая кредитованную, если у неё был подходящий клик.
    Каждая даёт один ассист. `organic` никогда не ассистирует.
*   Работа составляет O(число сессий + число кликов + ∑ числа активных кампаний по сессиям). Если в один
    день у каждого из N людей одна сессия и видны все C кампаний, цикл делает N×C посещений. При этом в
    `user_daily` всего N строк, в `campaign_daily` — C. В телеметрии фиксируются `assist_pairs`,
    максимум активных кампаний, максимальные размеры человека и время атрибуции. Стресс с общим
    устройством проверяет эту стоимость до выбора драйвера.

**`aggregate_user_day`.**

*   Сессии человека идут по возрастанию начала, поэтому дни не убывают.
*   Суммы копятся до смены дня, потом выводится строка `user_daily`.
*   `top_category` — ранг с наибольшей суммой, при равенстве меньший ранг.
    Без покупок он равен null. `revenue_cents` без покупок равен 0.
*   Ячейка `campaign_daily` для кредитованной кампании получает `sessions`,
    `purchasing_sessions` и `revenue_cents`.

### 7. Шаги правил, которые быстрый путь пропускает

Каждый пропуск записан в реестр правил как «пропущено». У записи есть
доказательство в одну фразу и защитный тест. Оракул выполняет эти шаги
буквально.

| ID правила | Шаг | Почему выход не меняется | Защитный тест |
| --- | --- | --- | --- |
| `CL.DEDUP` | Дедупликация кликов | Копии одинаковы [Факт: `rules.md:61`]. Выбор по (max `ts`, min `click_id`) и множество ассистирующих кампаний от повторов не меняются | Дополнительная фикстура: повторённые клики в разных кавычках |
| `LNK.REPEAT_SELF` | Повторы ссылок и ссылки на себя | Ничего не меняют в union-find | L2, L3 |

Окно клика проверяется для каждой физической строки. Повторённый клик за
границей окна даёт два физических отказа и один отказ после дедупликации.
Единицы счёта и доступность логических счётчиков определены в разделе 13.

### 8. Выход: контракт Parquet

*   **Библиотека.** Крейт `parquet` (arrow-rs) через низкоуровневый
    `SerializedFileWriter`, `default-features = false`, без Arrow (D5). Схема
    задаётся строкой message type.
*   `user_daily` содержит ровно `user_id, day, sessions, events, revenue_cents, top_category`. Ключ —
    `(user_id, day)`.
*   `campaign_daily` содержит ровно
    `campaign_id, channel, day, sessions, purchasing_sessions, revenue_cents, assisted_sessions`. Ключ —
    `(campaign_id, day)`.
*   `user_id`, `campaign_id` и `channel` используют required BYTE_ARRAY (STRING), `top_category` —
    optional BYTE_ARRAY (STRING), `day` — required INT32 (DATE, дни от эпохи). Все числовые показатели
    обеих таблиц — required INT64. Без покупки `top_category` содержит настоящий null.
    [Правила, Outputs](./.local/rules.md#outputs) и
    [схемы официального читателя](./.local/starter-duckdb/scripts/run_fixtures.py).
*   Формат — Parquet без сжатия, страницы данных v1, группа по 1M строк. Итоговые имена
    `part-<поток>.parquet` видны официальному читателю. Каждая таблица имеет хотя бы один файл с полной
    схемой, включая пустой результат.
*   `make readers-check` открывает **одни и те же сохранённые выходы кандидата** для E5 (две пустые
    таблицы), E8 (покупка) и E1 (просмотры с null) в Polars, PyArrow и DuckDB. Каждый читатель сверяет
    точные столбцы табличной схемы, строковые и целочисленные типы, логическую дату и значения с ручными
    CSV. PyArrow дополнительно проверяет физический INT32/DATE, UTF-8 и optional/required по Parquet
    metadata. Проверяется разница null и пустой строки. Проверка фазы 0 использует только две пустые
    фикстуры из матрицы. Полная трёхсторонняя проверка значений входит в фазу 3.

### 9. Память

Все бюджеты задаются байтами. Начальный проектный бюджет — **12 000 000 000 B**. Его увеличение до 16
000 000 000 B требует записи решения с измерениями на 60M и 120M. Эффективная граница — минимум
проектного бюджета, `MEM_GB × 1 000 000 000` и конечного `memory.max` cgroup. Фактическое значение для
Docker `--memory 24g` читается из ядра и хранится без пересчёта в условные «GB».

| Момент в `fast` | Пример полезной нагрузки на 60M событий |
| --- | --- |
| Конец шага 1 | 63,6M × 64 B (`EventRaw`) ≈ 4,07 GB и 15,5M × 48 B (`ClickRec`) ≈ 0,74 GB |
| Перекладка в шаге 2 | При одновременном удержании всех буферов записей 4,07 + 60M × 40 B + 2 × 0,744 ≈ 7,96 GB |
| Шаг 3 | 60M × 40 B и 15,5M × 48 B ≈ 3,14 GB до рабочих буферов |

Это оценки для планирования. Обе модели памяти учитывают ёмкость и рост `Vec`, хеш-таблицы (включая
`simple`), объединение ссылок, сортировки и перекос, массивы кампаний на поток, аллокатор, файловый
кэш/mmap, буферы Parquet и общие множества ключей выходных таблиц. Стартовый прогноз и пик самого
процесса (`getrusage(RUSAGE_SELF)`) идут в лог отдельными полями. Для MiB величину `ru_maxrss` переводят
из байтов на Darwin или KiB на Linux. Размер плотных массивов проверяется для всех работников вместе, с
учётом остальных живых буферов.

**Приёмка памяти.** На Linux-VM стенд создаёт свежую выделенную родительскую cgroup v2 для каждого
запуска и помещает в неё только контейнер кандидата через `--cgroup-parent`. Клиент Docker и подготовка
данных работают снаружи. Стенд ставит конечный лимит, запрещает своп (`memory.swap.max=0`), фиксирует
начальные `memory.events` (`oom` и `oom_kill`), фактический `memory.max` и настройки дочернего
контейнера. Родитель сохраняется до конца чтения статистики. После `docker wait` стенд снимает
иерархический `memory.peak` в байтах и дельты событий родителя, а до удаления контейнера —
`docker inspect State.OOMKilled` и код выхода. Даже уничтожение дочерней cgroup оставляет свидетельство
в родителе.

Для каждого допускаемого режима требуются обычный полный выход на 60M и стресс 120M, нулевые дельты OOM,
`OOMKilled=false`, выход 0, пик не выше эффективного бюджета. Нечитаемая метрика или включённый своп
оставляют проверку незачтённой. При превышении бюджета фиксируют измерение, пересматривают алгоритм или
ресурсное решение и повторяют обе проверки. RSS процесса — дополнительная метрика. Время и пик клиента
Docker для допуска не используются.

### 10. Реестры

Все реестры лежат в `spec/`. Каждая запись имеет стабильный ID.

*   **`spec/rules.toml` — реестр правил.** Поля записи:
    *   ID, например `CSV.CR` или `EV.DEDUP_BEFORE_VALIDATE`;
    *   строка `rules.md` и цитата;
    *   фикстуры;
    *   покрытие: фикстура, генератор, fuzz или никто;
    *   функция оракула;
    *   место в Rust и код причины;
    *   тесты;
    *   статус «выполнено» или «пропущено с доказательством».

    Порядок проверок у победителя события: непустой `user_id`, валидный `ts`
    в окне, допустимый тип, непустой `product_id`, цена **только у покупки**,
    затем опоздание. При чтении каждой копии вычисляется предварительный
    код. Судьба события определяется после выбора минимального `ingest_ts`.
*   **`spec/interpretations.toml` — реестр толкований.** Поля: правило,
    вопрос, выбранное прочтение, свидетельство, задан ли вопрос организаторам.
*   **`spec/assumptions.toml` — реестр допущений.** Поля: свойство данных,
    проверка во время работы, общий запасной путь, счётчик.
*   **`spec/mutations.toml`** связывает каждую мутацию с правилом и ожидаемым
    отличием. `make registry-oracle` проверяет ID, ссылки на правила и покрытие
    в `oracle/`, фикстурах и seed. `make registry-full` дополнительно проверяет
    метки в `src/` и `tests/` и проверку каждого допущения со счётчиком.
    `make mutation-check` запускает отдельную сборку `--features mutate` и
    фиксирует случай, на котором сработала каждая мутация. Выжившая мутация
    завершает эту цель ошибкой.

Начальные толкования:

| ID | Вопрос | Прочтение | Свидетельство | Организаторам |
| --- | --- | --- | --- | --- |
| `CSV.HEADER_BY_POSITION` | Что считать заголовком | Только строку со смещением 0. Строка, равная заголовку, в другом месте — данные | L3 (`links:11-13`) | нет |
| `CSV.LAST_LINE_NO_LF` | Последняя строка файла без `\n` | Это строка, она разбирается как обычно | Правила молчат, генератор так не пишет | да, вопрос 5 |
| `EV.EQUAL_COPIES` | Копии с равным `ingest_ts` | Верим `rules.md:51`, оставляем любую. Различие копий считается | `rules.md:51` | нет |
| `CL.COPIES_IDENTICAL` | Копии кликов | Производственный алгоритм допускает одинаковые повторы в оконном проходе. Оракул и диагностика сводят логические ID в B4 к множеству. | `rules.md:61`, A10 с повтором | нет |
| `EV.INGEST_TS_INVALID` | `ingest_ts` не F1 | Строка повреждена, растёт счётчик | `rules.md:34` обещает, что так не бывает | нет |

| `INPUT.UTF8` | Невалидный UTF-8 | Не проверяется, байты идут в выход как есть | `rules.md:22` обещает UTF-8 | нет |

Начальные допущения:

| ID | Свойство | Проверка | Запасной путь | Счётчик |
| --- | --- | --- | --- | --- |
| `ASM.ID_LEN_15` | ID не длиннее 15 байт | При кодировании ключа | Таблица переполнения и медленное сравнение | `assume.long_ids` |
| `ASM.SORT_KEY_31` | Окно плюс 7 дней короче 2^31 мс | При старте | Сортировка по паре `(LocalPerson, ts)` | `assume.wide_window` |
| `ASM.CAMPAIGN_DAY_DENSE` | `(C + 1) × D` не больше 8M и массивы всех работников укладываются в бюджет | Проверенное умножение размеров при старте | `HashMap` вместо массива | `assume.sparse_campaign_day` |

**Политика для AI-ассистента** записана в `CLAUDE.md` в корне:

*   `spec/rules.md` — единственная спецификация;
*   оракул пишется только по `rules.md`, до быстрого пути, без чтения
    исходников генератора и Rust-кода;
*   толкования принимаются только через реестр;
*   автор проверяет оракул правило за правилом, прежде чем ему доверять.

### 11. Контракт запуска и сборка

**Переменные окружения:**

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DATA_DIR` | `/data` | Вход |
| `OUTPUT_DIR` | `/output` | Выход. Подпапки бинарник создаёт сам |
| `SCRATCH_DIR` | `/scratch` | Временные файлы. `std::env::temp_dir()` не используется |
| `NCPU` | `std::thread::available_parallelism()` | Число потоков. Учитывает квоту cgroup |
| `MEM_GB` | 24 | Входной лимит в десятичных GB. Эффективный бюджет вычисляется в байтах по разделу 9. |
| `SS_MODE` | значение из `main.rs` | `simple` или `fast` |
| `SS_CHUNK_BYTES`, `SS_EVENT_BUCKETS`, `SS_PERSON_BUCKETS` | из фазы 1 и фазы 4 | Ручки для метаморфных тестов и подбора |
| `SS_DUMP_DIR`, `SS_MUTATION` | нет | Только в сборках с фичами `diag` и `mutate` |

**Аргументы.** Без аргументов бинарник использует каталоги из окружения. Два позиционных аргумента
переопределяют `DATA_DIR` и `OUTPUT_DIR`, как требует `run_fixtures.py`. В диагностической сборке
доступны `explain <user_id>`, `leaf` и `scan --io mmap` или `scan --io pread`. Обе команды scan читают
один и тот же вход и только делят его на строки и поля.

Официальный `docker_run.sh` передаёт фиксированный набор переменных. Он используется для проверки режима
образа по умолчанию. Для другого режима и тестовых параметров локальные цели запускают Docker напрямую с
теми же монтированиями, uid,
`--platform linux/amd64 --cpus 8 --memory 24g --memory-swap 24g --network none --read-only` и остальными
ограничениями штатного скрипта. Стенд явно добавляет `-e SS_MODE=fast` либо `-e SS_MODE=simple`, а также
нужные `-e SS_CHUNK_BYTES=…` и настройки корзин. При расхождении со стартовой JSON-записью прогон
отклоняется. Один только экспорт переменной родительской оболочки не передаёт её в контейнер.

**Стартовая строка в stderr** — одна строка JSON:

*   каталоги;
*   число и объём файлов по папкам;
*   окно;
*   число потоков;
*   эффективный байтовый бюджет, входной размер и прогноз памяти;
*   фактические режим, способ чтения, размер куска, числа корзин и рабочие потоки;
*   ID сборки.

ID сборки — хеш содержимого `src/`, `Cargo.toml` и `Cargo.lock`, его считает
`build.rs`. `.git` в контекст сборки не попадает, поэтому SHA коммита
недоступен. Журнал отправок сопоставляет ID сборки с SHA.

**Коды выхода.** `main` получает `Result<RunReport, RunError>` и сопоставляет `Config` с кодом 2,
`Input` с 3, `Output` с 4. Конфигурация, список файлов, чтение байтов, манифест, ссылки, потоки и
писатели сохраняют исходную ошибку и контекст пути или этапа. Ошибка одной строки данных учитывается
отдельно в судьбах строк.

| Код | Значение |
| --- | --- |
| 0 | Готово |
| 2 | Ошибка конфигурации: переменные, аргументы |
| 3 | Ошибка чтения входа: нет папки, плохой `manifest.json`, ошибка ввода-вывода |
| 4 | Ошибка записи выхода |
| 5 | Самопроверка: суммы `sessions` в двух таблицах не равны |
| 6 | Самопроверка: суммы `revenue_cents` в двух таблицах не равны |
| 7 | Самопроверка: сумма `assisted_sessions` меньше суммы кредитованных сессий, кроме `organic` |
| 8 | Самопроверка: повтор ключа `(user_id, day)` или `(campaign_id, day)` |
| SIGABRT | Непредвиденная паника в release с `panic = "abort"`. Оболочка Linux обычно показывает 134, нативный launcher может вернуть номер сигнала отдельно. |

**Самопроверки** (`rules.md:97` и уникальность ключей):

*   суммы `sessions` и `revenue_cents` в двух таблицах равны;
*   сумма `assisted_sessions` не меньше суммы `sessions` у кредитованных
    кампаний, кроме `organic`;
*   ключи обеих таблиц уникальны во всём выводе. Пакеты ключей всех писателей `user_daily` проверяет
    одно общее множество точных пар; `campaign_daily` проверяет свой полный поток. Вычисление сумм
    сохраняет независимость от проверки ключей.

Null в `day` исключён схемой: колонка `required INT32`.

**Публикация файлов и ошибки.** На каждый запуск стенд выделяет свежий выход. Писатели создают в
выходной файловой системе скрытые временные части, записывают данные, проверяют `flush` и закрытие групп
и footer каждого Parquet. Остальные временные данные идут в `SCRATCH_DIR`. При первой ошибке драйвер
прекращает выдачу новой работы и дожидается всех уже запущенных работников. Ошибка чтения возвращается
как `RunError::Input` (3), ошибка создания, записи, закрытия или переименования — как `RunError::Output`
(4) с путём и причиной.

После успешного закрытия всех частей драйвер переименовывает их в итоговые. Если публикация прервалась,
он убирает только собственные временные и уже опубликованные части этой попытки и сообщает сбой очистки
в stderr. Читатель запускается после завершения процесса. Код 0 требует обе полностью опубликованные
таблицы. При логическом нарушении (5–8) закрытые таблицы сохраняются для диагностики, печатаются все
нарушения и возвращается наименьший их код. Повтор использует свежий выход.
**Dockerfile** — многоэтапная сборка:

1. Сборочный этап использует проверенный в фазе 0 Linux/amd64 образ Rust с версией toolchain проекта.
   Внутрь копируются `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml`, `.cargo/` и `src/`
   **до** первой команды Cargo. Затем выполняется
   `cargo build --release --locked --target x86_64-unknown-linux-gnu`.
2. В итоговом `debian:bookworm-slim` остаётся бинарник, `sh` и `chmod`. Указываются `USER 1000:1000` и
   `CMD ["/app/shopping-sessions"]`. Работоспособность проверяется настоящим Dockerfile под Linux/amd64.

`run.sh`, `pipeline/` и `requirements.txt` из корня удаляются.

Целевые флаги x86 заданы в `.cargo/config.toml`. На Darwin Cargo собирает нативный бинарник для
разработки. Линковка GNU/Linux выполняется внутри Linux-этапа
`docker buildx build --platform linux/amd64 --load`. Если вводится специализированный AVX-путь,
инструкции выбираются во время работы после проверки поддержки.

### 12. Проверка правильности

```text
правила → независимый Python-оракул → 36 ручных ответов, дополнительные случаи и MATCH на dev
                 │
                 ├─► T2 (фаза 3), T2/T3 (фаза 4): обе таблицы против оракула
                 ├─► T4: все физические строки B1 и полный граф B2
                 ├─► T4: когорты Python → user_daily и вклады B5 тех же людей полного прогона
                 └─► T4: независимая свёртка всех B5 → полный campaign_daily
бинарник ──► метаморфные прогоны по матрице преобразований (две таблицы)
simple и fast ──► сравнение потока данных после появления fast
```

**Оракул** (`oracle/`):

*   **Чтение.** Файлы читаются как байты (`open(path, "rb")`). Строки режутся
    только по `b"\n"`. Модуль `csv`, текстовый режим, `splitlines()`,
    `int()` на непроверенных строках и `datetime.fromisoformat` не
    используются.
*   Код оракула пишется по правилам и ручным ответам, отдельно от Rust и генератора. Для одних и тех же
    входов обе реализации используют общий контракт наблюдаемых результатов.
*   Python пишет таблицы через Polars и дампы B1–B6 в формате раздела 13. В `oracle/leaf.py`
    документируются проверки физического LF, сохранения CR, ASCII-цифр, пустого поля и даты, каждая с
    примером из правил или фикстур.

**Проверка всех входных строк.** `oracle.py --rows DATA DUMP_DIR` и сборка Rust с
`diag` выдают B1 и B2. B1 — локальный результат разбора каждой физической
строки данных. Код проверки копии в B1 ещё ничего не говорит о победителе
дедупликации. В E5 ранняя невалидная копия определяет исход события, хотя
другая строка сама по себе проходит проверки. Для `raw` и B1 здесь физическими строками считаются строки
данных в `events/`, `clicks/` и `links/`. Манифест и чистые справочники проверяются при загрузке.

Для B2 отдельный первый проход читает **все** файлы ссылок, строит
union-find и фиксирует минимальные имена. Только после этого выводится одна
запись на ID из допустимых ссылок. В L2 связь `U7,u9` из второго файла
меняет имя для `u3` из первого. `make rows-oracle` требует независимого
совпадения **обоих** дампов на полном наборе.

**Выборка людей и проверка кампаний на T4.** `tools/sample_people.py extract DATA DST --rate R` сначала
строит граф по всем допустимым ссылкам. Имена — минимальные исходные UTF-8 байты в компоненте. Для ID
без связи из событий или кликов имя равно самому ID (E11).

1. Первый проход по событиям считает физические синтаксически разобранные строки с непустыми `user_id` и
   `event_id` по имени, до дедупликации и проверки времени, типа или цены. В когорту входят первые пять
   по убыванию счётчика и возрастанию байтов имени при равенстве, все компоненты более 50 ID (включая
   компоненты более 1 000) и каждое имя с `u64_be(SHA256(исходные байты имени)[0:8]) % 1000 < R`. `R` —
   целое от 0 до 1000, по умолчанию 1. Для хеш-выборки перечисляют ID из ссылок, событий и отдельного
   прохода по кликам, включая людей без событий.
2. Второй проход по событиям собирает все `event_id`, встреченные у выбранных имён, включая будущих
   проигравших и строки с ошибкой бизнес-поля. Третий проход копирует **все** синтаксически разобранные
   строки этих ID, независимо от пользователя, позиции или валидности победителя. Клики выбранных имён
   копируются отдельным проходом. Справочники, все ссылки и манифест копируются целиком. Файл
   `cohort.jsonl` хранит экранированные имена в порядке байтов, причины включения и параметры набора.
   Повтор запуска на тех же данных должен дать ту же когорту. Тесты включают E11 и более раннюю копию у
   другого человека.
3. Python-оракул считает поднабор. Перед сверкой `make sample-oracle` требует `MATCH` обеих таблиц
   диагностического и обычного полного прогона (один SHA, режим, вход и рабочие настройки). Для
   выбранных имён он сравнивает `user_daily` и записи B5 **полного** прогона Rust по ключу
   `(имя, начало сессии)`. Сверяются день, события, покупка, выручка, кредит и упорядоченное множество
   кампаний-ассистентов. Фильтр по когорте накладывается после разрешения владельца победителя.
4. Независимый Python-редуктор потоково складывает B5 **всех** людей полного прогона. Кредитованной
   кампании и дню он начисляет одну сессию, признак покупки и выручку. Каждой различной
   кампании-ассистенту — один ассист. Он сохраняет в том числе строки с ненулевыми ассистами и нулём
   кредитованных сессий и присоединяет канал из `campaigns.csv`. Для `organic` канал равен `organic` и
   ассисты равны нулю. Неизвестный ID кампании в B5 означает ошибку проверки. Весь результат по ключам и
   значениям должен совпасть с `campaign_daily` обычного прогона того же кандидата. Это проверяет и
   распределение между кампаниями, и агрегацию между людьми.
5. Контроль чувствительности использует A1/A6 с совпадающим `user_daily` и различным кредитом. На A11
   перенос кредита и 1 000 центов с `c_2` на `c_1` с сохранением глобальных сумм должен дать расхождение
   в выбранных сессиях, а перенос между строками готовой таблицы — в глобальной сверке. Положительный
   случай A11 сохраняет строку `c_1` с одним ассистом и нулями в трёх кредитованных метриках.

**Метаморфные тесты.** Для каждого преобразования меняется один фактор. Параметры кусков и корзин
испытывают в `fast`, у которого они управляют обработкой. Для `simple` испытывают число работников,
перестановки данных и равенство выходов с `fast`. Квитанция указывает, какой параметр действительно
менялся. Для метаморфных пар `compare.py` требует равенства обеих выходных таблиц. У выборки своя
область сравнения. Дополнительные сравнения зависят от сохранённого смысла записей.

| Пара прогонов | Сравниваемые границы |
| --- | --- |
| Одни байты входа при другом `NCPU` (1, 3, 8), числе корзин (1, 7, 512), размере куска или порядке выдачи работы | B1–B6 по каноническим ключам. B1 хранит исходную позицию независимо от разбиения. |
| Перекладка строк, файл только с заголовком, изменение кавычек без изменения значений, повтор и разворот ссылок, повтор кликов, добавление копий с заведомо более поздним `ingest_ts` | B2–B6. Физические строки и их позиции могут измениться. B3 содержит семантику победителя, B4 — множество логических кликов. |
| Полный вход и выборка | B2 на полном графе ссылок, затем выбранные B5 и `user_daily`. Независимая свёртка всех B5 сравнивается с полной `campaign_daily`. |

В T1/T2 упражнения на границы включают 64 B и смещения вокруг LF. Для одного входа 5 GB шаг 64 B дал бы
около 78 млн объектов очереди. В T4 сравнивают 1 MiB и рабочий размер (начальное значение 16 MiB), меняя
один параметр за раз. Стенд пишет B1–B6 в буферизованные потоки, переиспользует один опорный прогон и
обрабатывает по одному сравниваемому варианту. Открытые файлы и буферы ограничены числом работников и
партий слияния, даже если один файл содержит миллионы строк. После сверки успешного варианта
освобождаются его промежуточные дампы. При расхождении сохраняются параметры и первые отличающиеся
записи. Отдельный файл на строку или на 64 байта входа не создаётся. Количество Parquet-частей может
зависеть от числа работников. Корректность проверяется по объединённым строкам каждой таблицы.

**Остальные средства:**

*   **Усиление редких случаев.** Патч `tools/generator/dirt-scale.patch` вводит целый `--dirt-scale K` в
    диапазоне 1…16 с умолчанием 1. Нецелое и выход за границы дают код 2. Для долей применяется
    `min(1, K × p)` с сохранением исходной последовательности обращений к RNG при K=1. Масштабируются
    регистр ID, доли цепочек и общих устройств, плохие оригиналы, смена пользователя в пересмотренной
    копии, граничные клики и совпадение миллисекунд. Остальные вероятности сохраняются.
*   Контроль K=1 побайтно сравнивает файлы официального генератора с двумя запусками патченной версии
    (без флага и с явным K=1) на seed 1, 2, 3 при 10 000 событий и 2 500 кликов. Положительный контроль
    K=8 проверяет **каждый** механизм фиксированным выбором между старым и новым порогами и требует
    наблюдаемый случай в реально выпущенных строках или связях. Для воспроизведения используется пара
    наборов с тем же seed или малый детерминированный тест, вызывающий тот же код генерации. Один рост
    общего числа грязных строк эту проверку не закрывает. Проверяются изменение регистра ID
    событий/кликов, стороны ссылки и кампании, размеры цепочек и компонент общих устройств, плохая и
    пересмотренная копии, точное смещение граничного клика, пара с одинаковым временем. Игнорируемый
    старым бинарником флаг обязан провалить положительный контроль. Регистрируются свидетели, их
    счётчики и ключ набора.
*   **Идентичность набора.** Команда использует `--seed S --events E --clicks C --output DIR`. У
    патченного бинарника добавляется `--dirt-scale K`. Для поиска окон, кэша и воспроизведения
    фиксируются версия/хеш бинарника, S, E, C, K, значение `--threads`, каталог и хеш содержимого.
    Полный ключ задаёт отдельный каталог кэша для каждого набора. Параметры перебора окон — 1 000
    событий, 250 кликов, K=1. Сохраняются окна с 29.02.2028, на границе месяца/года и крайние количества
    файлов.
*   **Дополнительные фикстуры** `testdata/fixtures-extra/`. Они нужны для
    правил, которые не покрывает генератор или вообще никто:
    *   F3 и цена с ведущими нулями длиннее 20 символов;
    *   повторённые клики в разных кавычках;
    *   формы `"`, `"""`, `""x"`;
    *   ID длиннее 15 байт с общим префиксом;
    *   последняя строка без `\n`;
    *   окно, которое пересекает 29.02.2028.

    Ответ к каждой считается вручную и подтверждается оракулом.
*   **Fuzz.** Цели `cargo fuzz` для `csv::split_line`, `ts::parse`,
    `price::parse` и `key::encode` с `key::cmp_bytes` проверяют, что паники
    нет. Сверка листовых функций с Python идёт через подкоманду `leaf`. Она
    читает строки из stdin и печатает канонический результат разбора. Её
    вывод сравнивается с `oracle/leaf.py` на корпусе fuzz и на случайных
    строках из `tools/leaf_corpus.py`.
*   **miri.** Тесты модулей с `unsafe` запускаются под
    `cargo +nightly miri test` на малых входах.
*   **Мутации и словарь симптомов.**
    *   Фича `mutate` вместе с переменной `SS_MUTATION=<id>` ломает одно
        правило за раз. Примеры:
        *   обратная ничья;
        *   `>=` вместо `>` в разрыве сессии;
        *   граница 7 дней не включается;
        *   дедупликация после проверки;
        *   имя по первому встреченному ID.
    *   `tools/symptoms.py` записывает в `work/` тест, код выхода и изменение конкретного результата для

**Уровни проверок:**

*   **T1:** фикстуры и дополнительные фикстуры; dev.
*   **T2:** seed на 10k–200k событий, включая seed с поднятой грязью и

*   **T3:** seed на 1–5M событий с отношением кликов к событиям от 1:2 до 1:8.
*   **T4.** Два seed по 20M и один по 60M. Для каждого режима выполняются соответствующие масштабные

    Пробу полного Python-оракула на одном 20M проводят в записанных пределах времени и памяти.

### 13. Диагностика

*   **Счётчики в JSON.** По `raw` обе реализации считают физические строки
    данных до дедупликации: исход, пустой ID, синтаксическую ошибку и
    предварительную причину отказа по таблицам. Заголовки пропускаются.
    `event_winners` считает один исход на прошедший группировку `event_id`.
    Счётчики сессий и ассистов относятся к реальным сессиям и парам
    «сессия–кампания». В диагностической сборке и оракуле есть дополнительная
    группа `logical_clicks`. Она сначала оставляет один синтаксически
    разобранный клик на непустой `click_id`, затем считает валидные клики и
    отказы по причинам. Производственная сборка эту группу опускает. При
    сравнении используются группы, реально рассчитанные обеими сторонами.
    Повтор строки A10 с `ts == window_end` даёт два `raw`-отказа и один
    `logical_clicks`-отказ, таблицы совпадают с исходными.
*   **Дампы границ этапов.** Диагностические данные хранятся в `SS_DUMP_DIR`.
    Колонки разделены табуляцией. Внутри значений пробелы, непечатаемые байты
    и обратная косая черта кодируются как `\xNN`. Порядок строк задают ключи
    ниже. Строковые ключи сортируются по исходным байтам до экранирования. При выгрузке B2–B6
    используются исходные ID и имена категорий/кампаний: номера интернирования, корзин, локальных людей
    и ранги заменяются их байтовыми значениями.

    | Дамп | Запись и ключ сверки |
    | --- | --- |
    | B1 | Каждая физическая строка данных. Ключ — относительный путь с именем папки и числовое смещение. Поля или причина повреждения, разобранное время, локальный код проверки. |
    | B2 | Один ID допустимой ссылки и окончательное имя после обработки всего графа. Ключ — байты ID. |
    | B3 | Один победитель на `event_id`, включая невалидного. Ключ — `event_id`. Поля — минимальный `ingest_ts`, проекция кандидата и окончательный исход. |
    | B4 | Множество валидных логических кликов после проверки. Ключ — уникальный `click_id`. Поля — имя человека, `ts` и кампания. Диагностика нормализует дубликаты в обоих драйверах. |
    | B5 | Одна сессия по ключу (имя, `start_ms`). Поля — день, число событий, выручка, признак покупки, кредитованная кампания и отсортированное множество ассистов. |
    | B6 | Строки результата по ключу (имя, день) или (кампания, день), отдельно по каждой таблице. |
*   `tools/diff_stages.py LEFT RIGHT --profile identical|transform` читает первую применимую границу из
    таблицы преобразований и показывает до 20 отличий на первой разошедшейся границе. В B1 слияние идёт
    по паре (полный относительный путь внутри датасета, **числовое** смещение). Например, 64
    предшествует 128, а `events/part.csv` и `clicks/part.csv` различны. В B2 порядок задают байты ID, в
    B3 — исходный `event_id`, в B4 — логический `click_id`, в B5 — байты имени и числовое начало, в B6 —
    ключи таблиц. Физический путь проигравшего и число поздних копий в B3 не входят.
*   `explain <user_id>` в обеих реализациях читает заданный `DATA_DIR`, строит полный граф и выводит
    экранированные члены компоненты, происхождение строк, победителя и причины выбытия, сессии,
    выбранный клик и ассисты.
*   Официальный `scripts/compare.py EXPECTED ACTUAL` сравнивает целые строки и проверяет дубли ключей.
    `tools/compare_scorer.py EXPECTED ACTUAL` дополнительно показывает различия по ключам и колонкам по
    правилам раздела о диагностике скорера.
*   Нативные профили `perf` или `cargo flamegraph` помогают локализовать время. Профилирование не входит
    в измеряемый интервал квалификации.

## Alternatives Considered

Варианты A–Y объясняют выбор текущей конструкции и условия, при которых его стоит пересмотреть.

### Движок и язык

#### Alternative A. Векторная база для группировки клиентов

Правило объединяет только точные концы ссылок по транзитивности. Union-find прямо вычисляет компоненты и
позволяет выбрать минимальное имя. Поиск по сходству добавил бы отношения, которых во входе нет.

#### Alternative B. PySpark

Распределённые группировки доступны, но среда скорера выделяет один контейнер. Для целевого объёма
запуск ещё одного движка и обмен между процессами пришлось бы включать в сквозное время. Выбран один
локальный бинарник.

#### Alternative C. DuckDB или Polars в основном конвейере

SQL и операции по столбцам подходят для агрегации и независимой проверки. На грязном входе стартер
указывает конкретные расхождения DuckDB в трактовке quoted-empty и повреждённых строк. Использование
внешнего движка после собственного разбора потребовало бы передачи данных между двумя представлениями.
Оракул и стенд продолжают использовать Polars. [Замечания стартера](./.local/starter-duckdb/README.md).

#### Alternative D. Go как основной язык

Группировку и точную обработку байтов можно реализовать в обоих языках. Дизайн выбирает Rust для одного
общего представления записей, явного владения памятью и низкоуровневого писателя Parquet. Сравнительных
измерений реализаций на Go и Rust нет.

#### Alternative E. Готовые разборщики строк, времени и цены

Выбор определяется проверяемыми примерами. Нужны физический LF, сохранение CR, пустое значение после
декодирования кавычек, ASCII-цифры и проверка календаря. Скалярная функция реализует этот контракт один
раз для обоих Rust-драйверов. Любая замена проходит тот же корпус и сверку с Python.

### Поток данных

#### Alternative F. Дедупликация событий внутри корзины человека

Такая корзина теряет конкуренцию между двумя пользователями, названными копиями одного события. Сначала
нужен глобальный победитель по `event_id`, после него определяется человек. Публичная E4 различает эти
порядки. [Фикстура E4](./.local/starter-duckdb/fixtures/E4/).

#### Alternative G. Отбрасывание невалидных событий сразу при чтении

Ранняя копия с разбираемыми ключом и `ingest_ts` может выиграть, а затем выбыть. Удаление такой копии до
сравнения позволило бы более поздней пройти. Драйвер хранит код судьбы до выбора победителя.
[Фикстура E5](./.local/starter-duckdb/fixtures/E5/).

#### Alternative H. Распараллеливание по файлам

Целый файл даёт простую единицу работы для `simple`. У `fast` куски позволяют распределить крупный файл
между потоками. Оба читателя обязаны воспроизвести физические строки и смещения последовательного
чтения.

#### Alternative I. Материализация всех дедуплицированных кликов

У идентичных по правилу копий общий результат выбора кредита и общий набор ассистирующих кампаний.
`fast` может обрабатывать физические записи в окне, поддерживая число активных кликов каждой кампании.
Диагностический B4 отдельно восстанавливает множество логических ID и считает его по правилам раздела
13.

#### Alternative J. Слияние интервалов для ассистов

Обход активных кампаний прост для проверки и требует по одному посещению каждой пары «сессия–кампания».
При N людях с одной сессией и C активными кампаниями в один день получается N×C посещений и N+C выходных
строк. К вариантам со слиянием интервалов возвращаются, если `assist_pairs` и таймер на перекошенном T4
выявят дорогой этап. Оба алгоритма проверяются на ассистах без кредита.

#### Alternative K. Один объединённый цикл по человеку

Раздельные `sessionize`, `credit_and_assists` и `aggregate_user_day` предоставляют проверяемые границы
событий, сессий и выходных вкладов. Объединять их имеет смысл при измеримом выигрыше и сохранении тех же
проверок.

#### Alternative L. Отдельная компактная запись для невалидных копий

Один тип `EventRaw` упрощает сравнение всех копий и сохраняет причину выбытия. Отдельное представление
требует дополнительного пути при сортировке. Основанием для него станет измеренный вклад таких копий в
пик cgroup.

### Представление ID

#### Alternative M. Единая таблица интернирования всех ID

Индекс сокращает размер некоторых ключей, но требует общей вставки и восстановления исходных байтов для
сравнения. `IdKey` непосредственно хранит короткий ID, полные байты длинных ID хранятся в таблице
переполнения. Стоимость можно оценить по частоте длинных ID и времени синхронизации.

#### Alternative N. 64-битный хеш вместо полного ID

Коллизия объединила бы различные события или людей. Хеш пригоден для выбора корзины, а равенство и ничьи
разрешаются по полному значению.

### Проверка правильности

#### Alternative O. Полный Python-оракул на 20M и 60M

Оценка около 30 GB относится к объектному представлению 60M. Для 20M предусмотрена отдельная попытка с
заданными пределами времени и памяти. Проверки полных B1/B2, выбранных сессий и всех кампаний проводятся
для каждого набора T4 независимо от исхода этой попытки.

#### Alternative P. Вторая независимая быстрая реализация

Вторая реализация внесла бы дополнительную трактовку всех правил. Для T1–T3 есть независимый
Python-оракул. На T4 он проверяет строки, имена, сессии выборки и выполняет полную свёртку кампаний. Для
общей ошибки, ускользнувшей от этих проверок, можно независимо переработать конкретный этап.

#### Alternative Q. Запасная отправка на DuckDB

Для такого кандидата потребовались бы полный входной диалект и самостоятельная квалификация. Первый
прошедший допуск `simple` уже даёт проверенный SHA и остаётся доступен для последующих сравнений.

### Структура кода и стенда

#### Alternative R. Две Rust-версии без общего кода

Общий слой стабилизирует трактовку правил в `simple` и `fast`. Их попарная сверка проверяет перемещение
и владение данными. Ручные ответы и независимый Python проверяют общие функции.

#### Alternative S. Сохранение простого драйвера только в Git-теге

Два режима одного образа позволяют чередовать прогоны на одинаковом исходном коде, машине и входе.
Отдельный тег сохраняет проверенный SHA для отправки. Нарушение самопроверки возвращает предусмотренный
код и сохраняет выход для разбора.

#### Alternative T. Стенд в отдельном репозитории или подмодуле

Один коммит однозначно задаёт версию кандидата, фикстур, инструментов и критериев. Изоляцию релизного
образа обеспечивает разрешающий список входов сборки.

### Сборка и запуск

#### Alternative U. Привязка всего бинарника к `native` или x86-64-v4

Инструкции машины сборки могут отсутствовать на машине запуска. Используется базовая целевая
конфигурация Linux/amd64. Более узкие ветви включаются после проверки CPU и сравнительных измерений.

#### Alternative V. Rayon для организации параллелизма

Статические этапы уже делят работу на куски и корзины с барьерами и фиксированным числом писателей.
Текущая схема использует стандартные потоки. Замена исполнителя требует проверки памяти, распределения
самой тяжёлой корзины и сквозного времени.

#### Alternative W. `ArrowWriter` вместо `SerializedFileWriter`

Две фиксированные схемы можно записать напрямую типизированными колонками и уровнями определённости.
Низкоуровневый писатель исключает промежуточный Arrow batch. Допустимость результата проверяют
официальные скрипты и три независимых читателя.

#### Alternative X. Передача SHA через Docker build argument

Официальный запуск не обещает пользовательских аргументов сборки. Бинарник вычисляет воспроизводимый
идентификатор из входов сборки, а квитанция стенда связывает его с образом и точным SHA.

#### Alternative Y. `panic = "unwind"` с перехватом в `main`

Ожидаемые ошибки конфигурации, чтения и записи моделируются через `Result` и сохраняют контекст
операции. Логические нарушения имеют коды 5–8. Профиль release использует `panic = "abort"` для
непредвиденной ошибки программы.

## Non-Functional Requirements

### Производительность

*   `scan --io mmap` и `scan --io pread` измеряют чтение и выделение строк на одинаковом входе. Сквозное
    время содержит запуск контейнера, разбор, дедупликацию, сортировку, обход людей, запись и закрытие
    результата. Отдельные таймеры показывают чтение, ссылки, слияние, запись и долю последовательной
    работы.
*   Сравнение драйверов использует один SHA, образ, неизменяемый набор, конфигурацию и машину. Для
    каждого состояния кэша чередуются `simple` и `fast`. На 60M нужны минимум три холодных и три тёплых
    прогона **каждого** кандидата. На выделенной Linux-VM холодный запуск следует за синхронизацией
    записей и сбросом файлового кэша. Перед тёплым запуском последовательно читают те же входные файлы.
    Способ подготовки и успешное выполнение записываются для каждой попытки. Каждый запуск получает
    свежий выход. Таймер использует моменты старта и остановки workload-контейнера. Сборка, подготовка
    кэша и последующая сверка находятся вне интервала. Фиксируются фактический image digest, SHA, режим,
    seed и хеш данных, число входных байтов и все лимиты. До фазы 4 на большом входе проверяют
    самопроверки и равенство обеих таблиц повторному прогону. С фазы 4 требуется также соответствующая
    независимая проверка T4.
*   Переход на `fast` допускается при прохождении всех его проверок и если для холодной **и** тёплой
    серии `median(simple) − median(fast) > max(размах simple, размах fast)`. Размах равен максимуму
    минус минимум. При ничьей, отрицательной разнице или недостаточном запасе сохраняется `simple`.
    Пример: `fast` за 60 с при `simple` за 40 с условие не проходит. После смены умолчания
    квалифицируется точный образ отправляемого SHA.

### Память

*   Для каждого квалифицируемого режима стенд проверяет 60M и стресс 120M в отдельной cgroup v2 без
    свопа. Критерии и единицы заданы в разделе 9. Время 120M фиксируется для диагностики.

### Безопасность и приватность

*   **Публичный репозиторий.** Секретов в нём нет.
*   **Файлы со страницы трека.** `generator.zip` и `dev-answer.zip` не
    коммитятся: право на распространение не подтверждено.
*   **Сеть.** Во время работы сети нет. Все зависимости ставятся при сборке
    образа.

### Выпуск и откат

*   Стартер допускает отправку по SHA и по вершине ветки по умолчанию. Проект выбирает явный SHA.
    Локальный тег `sub-NNN` привязывает квитанцию проверки к этому коммиту.
    [Контракт отправки](./.local/starter-duckdb/README.md).
*   `presubmit` проверяет чистое дерево и режим точного образа, пишет только в игнорируемый
    `work/qualification/`. После фактического ответа отдельное изменение `spec/submissions.md`
    записывает отправленный SHA, ID образа/сборки, режим, время и дословный ответ. Новый коммит журнала
    не меняет уже проверенный SHA. Повтор проверки тега создаёт новую квитанцию.
*   Способ выбора финальной попытки и доступность отката требуют подтверждения регламентом
    организаторов. Сохранить источник и дату в `spec/scoring.md`. При подтверждённой возможности выбрать
    попытку — записать выбранный SHA и подтверждение платформы. Иначе использовать только
    документированное действие, сохранить подтверждение принятой отправки и явно отметить статус
    финального выбора.

## Detailed Implementation Plan

### Фазы

<a id="qualification"></a>

#### Критерии допуска

Эта таблица задаёт проверки для `Makefile`, сценария отправки и финального
кандидата. Каждая следующая фаза использует уже работающий результат. Фазы 1
и 2 могут идти параллельно после фазы 0.

| Фаза и результат | Команда | Условие перехода |
| --- | --- | --- |
| 0 · Каркас | `make scaffold-smoke` | Из чистой сборки нативный бинарник и amd64-образ создают два Parquet с точными схемами и нулём строк на E5 и E13. Оба запуска завершаются кодом 0. |
| 1 · Чтение | `make scan-bench` | Оба способа чтения дают те же строки и смещения, что и чтение целого файла. Записаны выбранный способ, проверочная сумма, время и условия кэша на нативном Mac и на Linux (n2, 8 vCPU, холодный и тёплый кэш). |
| 2 · Независимый оракул | `make generator-check oracle-fixtures oracle-dev registry-oracle` | Проверены побайтовый контроль K=1, положительные случаи K=8 и отказ неверного K. Python проходит 36/36, дополнительные фикстуры и публичный dev. `registry-oracle` проверяет реализацию и покрытие правил в оракуле. |
| 3 · Первый `simple` | `make qualify-simple` | Тесты Rust и Clippy успешны. `registry-full` проходит. 36/36 и все дополнительные случаи проходят нативно и в amd64. `readers-check` проходит, свежий dev даёт `MATCH`. На всех T2 из реестра (включая високосное окно и K>1) обе таблицы совпадают с оракулом. На Linux проходят проверки памяти `simple` на 60M и 120M из раздела 9. Каждый из трёх холодных и трёх тёплых сквозных прогонов 60M ≤120 с. |
| 4 · Квалификация `fast` | `make qualify-fast` | Проверки фазы 3 для доступных режимов, совпадение `simple` и `fast` на T1–T4, обоих с полным оракулом на T1–T3 и все проверки T4 из раздела 12 для обоих режимов. Каждый fuzz-таргет проходит час, Miri проходит малые тесты с `unsafe`, отдельная сборка `--features mutate` обнаруживает каждую мутацию на фикстуре или T2. На Linux оба режима проходят проверку памяти. Переход на `fast` требует выигрыша в парном сравнении из раздела «Производительность». |
| 5 · Изменение после профилирования | `make presubmit` и парный замер | Кандидат проходит квалификацию своего режима. Замер на том же наборе показывает выигрыш против последней квалифицированной версии по критерию раздела «Производительность». |
| 6 · Фиксация результата | `make presubmit` на финальном теге | Проверен фактический режим образа. На 60M каждый из трёх холодных и трёх тёплых прогонов укладывается в 120 с. Автор сохраняет SHA и подтверждение отправки. |

**Фаза 0. Каркас.** Собрать генератор, подготовить Python-окружение, перенести
правила, официальные фикстуры и скрипты. Собрать Rust-бинарник, который читает
манифест и закрывает два пустых Parquet. Для `scaffold-smoke` стенд создаёт
временный корень только с E5 и E13, затем запускает штатную сверку для нативной
сборки и настоящего Docker-образа. Ошибка схемы, отсутствующая таблица или
ненулевая строка даёт ненулевой код. У остальных 34 официальных случаев есть
ожидаемые данные. Полный прогон по фикстурам, dev-сравнение и каталог
дополнительных случаев входят в последующие фазы. Удаление Python-заготовки
входит в тот же результат, в котором этот каркас уже собирается.

**Фаза 1. Замер чтения.** Подкоманда `scan` впервые использует `csv::split_line`
и два источника байтов. Зафиксировать нижнюю границу чтения и разделения полей
на 60M, выбрать способ чтения для Linux и записать условие эксперимента D9.
Разбиение проверяется на пустом файле, заголовке, длинной строке и разрезах вокруг LF.

**Фаза 2. Оракул и реестры.** Реализовать независимый Python-оракул, патч
генератора, отбор seed и дополнительные ручные ответы. Заполнить записи
правил и источники тестовых данных. Здесь достаточно меток в `oracle/` и
воспроизводимого свидетельства для каждого правила. Ссылки на ещё не
созданные Rust-модули и результаты мутаций проверяют следующие фазы.

**Фаза 3. Первый кандидат.** Подключить общий слой правил, `simple`,
счётчики, самопроверки и полный вывод таблиц. `make diff MODES=simple`
сравнивает этот режим с оракулом на T2. После успешного `presubmit` автор
может отправить тег `sub-001` по SHA. Ответ практики записывается отдельно
после получения. По первой засчитанной отправке автор уточняет числовую цель
для следующих кандидатов.

**Фаза 4. Квалификация быстрого драйвера.** Добавить `fast`, диагностику
B1–B6, проверки на выборке людей, сверку полной агрегации кампаний, fuzz и
мутационные тесты. Сначала испытать оба режима одного образа явно. Если
`fast` выполняет критерии точности, памяти и скорости, выбрать его режимом
по умолчанию в новом кандидате и снова проверить фактический образ по тегу.
При отсутствии выигрыша сохраняется квалифицированный `simple`.

**Фаза 5. Оптимизация.** Испытывать `memchr`, SWAR, затем SIMD с проверкой
инструкций во время работы только на измеренном узком месте. Сначала сверить
`leaf` со скалярной версией на x86. Изменения CPU, libc и аллокатора
сравниваются по одному на одинаковых данных и оборудовании.

**Фаза 6. Финальный SHA.** Пройти последнюю строку таблицы, отправить SHA в
срок и сохранить подтверждение. Способ выбора финальной попытки определяется
подтверждённым регламентом в `spec/scoring.md`.

## Решения по двум практическим отправкам, 22 ноября 2026

1. Простой Rust-драйвер используется для локальной сверки. Обе попытки выделены параллельному драйверу. На машине разработчика проверяются фикстуры, T2 и ограниченные случаи T3. Наборы 20M, 60M и 120M локально исключены по ограничению памяти пользователя. Скрытые 20M измеряет организатор. Измерения T4 и финала нельзя подменять экстраполяцией.
2. Первая попытка получила 3,83 с на скрытой практике. Рабочая цель второй итерации — 3,0 с на практике и 12 с на финальном наборе. Второе число остаётся целью до официального финала.
3. Вторая версия выбирает победителя внутри каждой независимой корзины хеш-таблицей, использует векторное распознавание пунктуации в строках 16–128 байт, плотный накопитель кампаний при достаточном бюджете и параллельную запись Parquet. Сравнение на публичном dev отдельно проверяет точное совпадение обеих таблиц в каждом замере. Для длинных строк сохраняется полный скалярный разбор. Измерения находятся в spec/timings.md.
4. Практика засчитала `sub-002` за 2,62 с и автоматически выбрала этот SHA для финала. Парные разборы пяти изменений на открытом наборе опубликованы вместе с первичными измерениями. [Вклад изменений](spec/timings.md) · [Подтверждения отправок](spec/submissions.md)
